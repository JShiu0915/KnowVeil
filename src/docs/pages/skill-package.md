## 送审的是什么 {#what}

送审时提交的是一个 **Skill 包**：一个待发布的能力单元，带有**展示名称**与**语义化版本号**（例如「合同审查助手 v1.2.0」）。

每个 Skill 在组织内有唯一标识（slug），用于检索、下载与链接；展示名称可以随版本优化，但标识一旦发布不宜随意更改，以免同事书签与安装脚本失效。

## 包里有什么 {#contents}

Skill 包是一个文件夹（或打成 ZIP 上传），至少包含：

| 部分 | 作用 |
| --- | --- |
| 入口说明文件 | 给 AI 与人类读者看的使用说明：做什么、何时用、步骤与边界 |
| 元数据 | 名称、摘要、版本号等，写在入口文件开头的结构化头信息中 |
| 可选参考文档 | 长说明、政策原文摘要等放在附属目录 |
| 可选示例 | 输入输出样例，帮助审查与同事理解 |
| 可选脚本 | 若包含脚本，仅作静态检查对象，**发布检查不会执行它们** |

**Web 发布时还需在表单中填写：**

- 分类（便于检索）  
- 版本标签（首个版本须包含 `latest`，表示默认安装线）  
- 变更说明（方便同事判断要不要从旧版升级）

包过大时，建议自行压缩为 ZIP 再上传；单包有大小上限，以当前部署说明为准。

## 送审前自查 {#self-check}

在提交 {{skill}} 之前，作者可先对照下列项，减少退回次数：

| 检查项 | 说明 |
| --- | --- |
| 摘要是否完整 | 一句话说明「做什么」和「什么场景下用」，避免空泛或重复堆砌 |
| 版本号是否递增 | 同一 Skill 的新版本号必须高于已发布版本，且符合语义化版本习惯 |
| 首个版本标签 | 第一个版本是否包含 `latest` 标签 |
| 步骤是否可执行 | 同事把说明交给 AI 后，能否按步骤完成，边界与例外是否写清 |
| 权限与工具是否如实声明 | 若 Skill 需要读文件、联网等，是否在说明与元数据中声明 |
| 脚本与外链 | 是否解释用途；避免未说明的破坏性操作或敏感路径 |
| 示例与验收 | 是否提供至少一个示例或验收标准，供质量审查对照 |

> [!TIP]
> 在 {{knode}} 里把流程跑通后再打包，入口说明可直接提炼已验证的步骤，减少「纸上 Skill」。

送审后，格式、质量、安全三道检查一次完成，结论含义见 [检查规则与结论含义](/docs/skill-checks)。
